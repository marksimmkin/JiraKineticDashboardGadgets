# Kinetic Jira dashboard gadgets

Eleven Forge Custom UI gadgets for **classic Jira Cloud dashboards**:

- **Controller**: configure named JQL filters with optional Start Date and End Date through the gadget's Edit action, then select the active filter in view mode.
- **Simple Counter**: counts issues matching that JQL in the statuses shown by the Controller, for the current Jira user. It shows Jira's approximate count first, marked "about", then the exact count when it is ready. It updates when the selection changes or the dashboard refreshes.
- **Simple Dates**: shows the selected filter's Start Date and End Date. Missing dates are shown as “Not set”.
- **Status Bar Chart**: counts issues for each Jira status name selected in the Controller, including zero-count statuses. Jira statuses that share a name are grouped into one bar.
- **Weighted Progress Bar**: compares calendar time elapsed with weighted work completed for the selected JQL. It requires dates for the upper half and a weight for every matching status for the lower half.
- **Weighted Burndown**: plots daily weighted remaining work against a straight-line ideal from the score at the start of the Start Date to zero at the end of the End Date. It reconstructs historical status weights from Jira issue changelogs.
- **Status Pie Chart**: shows the Controller's configured statuses as slices, with counts and percentages for the issues in those statuses.
- **List**: shows matching issues in JQL order by default, 50 at a time. Click a column heading to sort all matching issues by that field, ascending first, then descending on a second click. The sort replaces the filter's own ORDER BY and stays in place when the Controller filter changes or the dashboard refreshes, until the gadget reloads; it isn't saved. Fields that Jira can't sort by show an error instead. Configure and reorder up to 10 Jira field columns in this gadget's Edit view; custom fields are available from Jira's field catalogue.
- **User List**: groups matching issues by assignee and current status, including Unassigned issues.
- **User Leaderboard**: ranks assignees by the sum of their issues' remaining status weights. It includes Unassigned and requires weights for all matching statuses.
- **Capacity**: compares each assignee's Remaining Estimate, in days, with the working days (Monday to Friday) left until the selected filter's End Date. Over 100% is marked Overallocated and under 25% Underallocated. Someone with no remaining estimates is marked No estimates. Unassigned work is listed without a judgement. Set hours per day (default 8) in this gadget's Edit view.

The User List and User Leaderboard can show total tickets, total weighted score or total time remaining. Time remaining is the sum of each issue's Remaining Estimate, shown in days and hours, such as 6.0d (42h). Set hours per day (default 7) in each gadget's Edit view; it is separate from Capacity's setting.

Add one Controller and any of the other gadgets to the same dashboard. The Controller sends the selected filter's JQL, optional dates, and configured Jira status names through Forge bridge events, scoped to the dashboard ID. Dates are sent as `YYYY-MM-DD` strings or `null` and do not change the JQL. A period includes both dates: it runs from the start of the Start Date to the end of the End Date in the viewer's Jira time zone, so the two dates can be the same day. Each status name has a weight from 0 to 1 for the weighted gadgets; the Status Bar and Pie Charts show issue counts and do not apply those weights. The counter and list use the JQL narrowed to shown statuses and ignore the dates. Capacity uses the Start Date and End Date to count working days left and needs an End Date. The first saved filter is selected after a dashboard reload. Each selection carries a revision that changes when a filter is clicked (including the active one) or the dashboard or Controller is refreshed, so a gadget loads each selection from Jira once: repeats are ignored, and on a dashboard refresh the gadgets wait for the Controller's new selection rather than reloading on their own as well. If the Controller has not answered after 3 seconds, each gadget reloads once by itself. Refreshing a single display gadget reloads only that gadget (refreshing the Controller reloads them all); Simple Dates redraws the dates it already holds. A superseded load stops before requesting further Jira pages. When Jira rate limits a request (HTTP 429, or 503 with `Retry-After`), the gadget waits for `Retry-After` (or backs off 1, 2 and 4 seconds when it is missing), retries up to 3 times, and otherwise shows "Jira is busy. Try again in N seconds."; it does not wait longer than 30 seconds at a time. Configuration is stored by Jira with the Controller gadget; saved statuses from earlier versions are merged by name, keeping the first weight when duplicates existed.

The Controller's status dropdown shows statuses in active Jira workflows. If a weighted gadget reports a status that is missing from the dropdown, use **Add missing status** and enter the name shown by the gadget with its weight. Saved missing names remain editable if a workflow changes or the Jira status list cannot load. The Weighted Progress Bar inspects current issue statuses; the Weighted Burndown also uses historical status names from issue changelogs.

The Weighted Progress Bar uses the issues currently matching the JQL as its work scope, including completed issues. Its work percentage is `1 - sum(status weights) / matching issue count`, so scope changes can change the percentage. Unmapped statuses prevent a work percentage and are listed for configuration; zero matching issues are shown as an empty state. Its time percentage counts whole days elapsed: 0% on the Start Date, 100% once the End Date has passed. The today marker sits at the start of today.

The Weighted Burndown uses that same current JQL scope and adds an issue's score on its creation day. It starts with the score at the beginning of the Start Date, then plots each day's end-of-day score at the end of that day, through today or the End Date, whichever comes first; today's point shows the current score so far. Changes on the Start Date appear as a step at the end of the first day. The ideal line starts at the beginning-of-day score and reaches zero at the end of the End Date. Changing the JQL scope or status weights can redraw historical values; this is a reconstructed chart, not a stored sprint snapshot. It requires weights for every status shown in the plotted period.

The Status Pie Chart uses the same configured status names as the Status Bar Chart. Percentages are calculated among issues in shown statuses; the message below the chart reports how many of all JQL issues those statuses cover. The User List, User Leaderboard, and Capacity show only statuses listed in the Controller with Show ticked; issues in other statuses are left out. The leaderboard uses the Controller weights.

Each Controller status has a **Show** tick box. Unticked statuses are hidden for every viewer from the Simple Counter, List, Status Bar Chart, Status Pie Chart, User List, User Leaderboard, and Capacity, and each of those gadgets shows a short "Hiding:" note. Done-category statuses start unticked, and Done-category statuses not listed in the Controller are hidden too. The Status Bar Chart, Status Pie Chart, User List, User Leaderboard, and Capacity also leave out every status not listed in the Controller. The charts still show the total JQL issue count as context. The progress and burndown gadgets continue to use the full JQL scope.

Issue-count numbers throughout the gadgets open Jira's standard issue navigator in a new tab. Status counts add the matching status IDs to the selected Controller JQL, and assignee counts add the relevant Jira account ID (or `assignee is EMPTY`). Weighted scores, percentages, dates, and counts of people are not issue counts and do not open issue lists.

## Setup

The source uses `@forge/bridge` for Jira and `esbuild` for the browser bundles. Use Node.js 24 (24.22.1 or later), which matches the app's `nodejs24.x` runtime and Forge CLI 15. On macOS: `brew install node@24 && brew link --overwrite --force node@24`, then reinstall the CLI with `npm install -g @forge/cli --allow-scripts=@forge/cli,cloudflared,keytar` (npm 11 blocks install scripts unless they are allowed, and the CLI needs them to store your login).

1. Run `npm ci`, `npm run build`, and `npm test`.
2. For development changes, run `forge deploy -e development`. After validating a release, run `forge deploy -e production`. Both environments are installed on `kineticgames.atlassian.net` in Jira; use the production gadgets (without the DEV label) for shared dashboards.
3. Add the Controller and the other gadgets to a classic dashboard. Open the Controller's Edit action, add a named JQL filter with optional dates and Jira statuses with weights and whether each is shown, and save.

This app is registered in **Kinetic App Developer Space**. Keep the app ID in `manifest.yml`; running `forge register` again would create a different app registration.

For colleagues who are not app contributors, set **Distribution** to **Sharing** in the Atlassian developer console. The production Controller and development Controller keep separate gadget configurations, so configure the production Controller on the shared dashboard.

The counter first shows Jira's approximate issue count, then uses Jira's enhanced JQL search and follows all pages to replace it with an exact count of issues visible to the current user. Very large filters may take longer to show the exact count. If the exact count fails, the approximate count stays with a message. Jira search results can briefly lag recent issue changes.
